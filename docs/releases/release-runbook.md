# Release and rollback runbook

P17 tooling is prepared; P16 acceptance remains open. No new release has been tagged or deployed. Keep v0.1.0-beta.1 as the historical published version until an accepted successor exists.

## Prepare

1. Close the outstanding checks in docs/audits/p16-acceptance/assessment.md, including real-browser recovery, physical-device usability, large-scene performance and domain review. Record evidence, not just a green automated suite.
2. Review redistribution.md and imported-file/security qualifications below. Retain dependency licence notices. Choose the next version; update package.json/package-lock.json together, create release notes and commit the complete reviewed source. Never tag a dirty working tree as if it contains the edits.
3. On Node 24, run `npm ci`, `npm audit --audit-level=high`, `npm run lint`, `npm test`, `npm run test:release`, `npm run build -- --base /UMC_Ship_Stability/`, and `node scripts/verify-hosting.mjs dist /UMC_Ship_Stability/`. For a local preview of the subpath build use `npm run preview:pages -- --host 127.0.0.1 --port 4197 --strictPort` and open `/UMC_Ship_Stability/`; the preview base must match the build base. Repeat the build at `/` for root-hosted distributions. Record Node/npm versions, source SHA, commands and results.
4. Run `node scripts/release-notices.mjs dist` to include LICENSE.txt and locked runtime dependency notices in dist. Run `node scripts/release-tools.mjs manifest dist SOURCE_SHA VERSION_TAG`, then `node scripts/release-tools.mjs verify dist SOURCE_SHA VERSION_TAG`. The sorted manifest records SHA-256/size for every artifact file and detects missing, extra or changed assets. It is an integrity inventory, not a signature or independent authenticity proof. Keep it with an immutable archive and corresponding source archive. Do not modify assets afterward.
5. Rehearse rollback below. After explicit release authorisation, create the version tag on the reviewed source commit. In a subsequent default-branch commit, set release-gate.json to that exact tagged commit SHA and tag, with named reviewers/evidence for acceptance, redistribution and rollback. Keeping approval separate avoids a self-referential commit SHA. Evidence must point to nonempty regular files under `docs/` in that approval commit; absolute paths, traversal and symlinks are rejected. Validate with `node scripts/release-tools.mjs gate release-approval/docs/releases/release-gate.json SOURCE_SHA VERSION_TAG release-approval` when using a separate approval checkout. File existence does not replace human review of the evidence.
6. In Actions, run Check and deploy website against that tag with deploy enabled. Pushes and pull requests only check/build; they no longer deploy. A branch dispatch cannot pass the version-tag gate. The default branch holds the current approval record; the tagged source supplies the build. Review the workflow/environment permissions before dispatch.
7. Archive the exact deployed artifact and source; publish checksums, release notes, quick-start, known limits and evidence. Verify the release-manifest.json SHA/tag on the hosted site. Do not call a local preview a deployed smoke test.

## Smoke test and rollback rehearsal

Before release, retain the previous immutable artifact/source SHA and its deployment run. In an isolated browser profile at the same test origin: save/export a previous-version plan; load it in the candidate; edit cargo/support and tank contents; save/export a candidate plan and voyage backup. Record mass, centres, tank fills, selected vessel, warnings and report revision. Stop the candidate server and serve the retained previous artifact at the same origin. Check previous plans still open and candidate backups either import correctly or reject clearly without damaging existing storage. Re-serve the candidate and verify its saved data and exports. Keep all original backup files. Unsupported backward import is not a reason to erase or migrate storage.

Production smoke: fresh session → choose vessel → onboard weights/liquids → cargo and support → ballast → assessment/3D → named save and JSON export → reload/reopen → clean-profile import and report. Check English/Romanian, deployed subpath assets/source links, missing-resource and offline messages. Record actual results in the release evidence. Do not claim unrestricted offline use: there is no offline cache guarantee.

If production fails, stop publication, retain exports and restore the exact previous verified artifact using an authorised deployment. If rebuilding an old source, use its lockfile and Node version and compare artifact evidence; a rebuild is not necessarily byte-identical. This new workflow does not exist in historical tags: do not assume an old tag's workflow has the new gate. An operator must review the recovery workflow before dispatch. Do not clear browser storage, change the hostname/base path, or perform destructive migrations to roll back. Verify same-origin plan reopening after recovery, then record the incident under its owning roadmap stage.

## Security and data boundaries

Existing ship imports bound file count/bytes and validate relative paths and referenced assets; report exports escape text. Regression tests cover invalid inputs. This is not an independent security audit. Recheck hostile SVG/glTF/data URI, imported URLs, oversized plan/resource exhaustion and HTML/export handling before declaring security acceptance. Keep raw documents, credentials, browser storage and user plans out of release archives. The artifact inventory rejects source directories, symlinks, source maps, PDFs, workbooks and CAD files. No telemetry or automatic user-data upload is introduced.
